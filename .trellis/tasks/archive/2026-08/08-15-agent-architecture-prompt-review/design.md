# MCBE Chat Agent 架构与提示词审查设计

## 交付物

- 新增 `docs/review/mcbe-chat-agent-architecture-prompt-review-20260815.md`。
- 仅形成文字版审查报告，不修改业务代码、配置、协议或测试。
- 报告以当前 `dev` 提交为代码快照，并注明调研日期、版本边界和复现方法。

## 证据模型

### 外部资料

按以下优先级采信：

1. 官方 API / SDK / CLI 文档、公开源码、协议规范；
2. 官方工程文章和维护者说明；
3. 论文、标准和安全组织资料；
4. 二手文章仅用于补充观点，不作为核心结论的唯一证据。

OpenAI / Codex 只使用 OpenAI 官方网站和 `openai/*` 官方仓库核验；库与框架 API 通过 Context7 官方资料核验；网页广度调研使用 Firecrawl 彻底档。MCP 以调研时最新 `2026-07-28` 规范为主，同时明确项目 SDK 可能仍实现旧协议，避免把未来接口直接当作当前代码缺陷。

### 仓库结论

每项重要发现标成以下一种：

- **已确认缺陷**：源码路径、框架语义和离线复现能共同证明实际行为错误；
- **设计风险**：代码存在明确攻击面、漂移点或失效条件，但没有生产事故证据；
- **改进机会**：当前行为可用，优化主要提升效率、可维护性或评测能力。

严重级别采用：

- **P0**：可能泄露凭据、破坏权限边界，或让核心执行/审计事实失真；
- **P1**：会影响常用功能正确性、上下文稳定性或高频运行质量；
- **P2**：可维护性、成本、可观察性或长期兼容性问题。

## 调研与审查方法

1. 用不少于 10 个检索角度覆盖 OpenAI/Codex、Anthropic/Claude Code、PydanticAI、LangGraph、MCP、安全和评测。
2. 汇总不少于 25 个有效来源，核心主张在正文就近链接，并在末尾给出来源目录和 Firecrawl 复跑输入。
3. 从 `Gateway -> MessageBroker -> AgentWorker -> PydanticAI Agent -> 运行时 Harness -> 工具/AddOn/MCP -> BrokerResponseBridge` 追踪完整运行路径。
4. 分别审查提示词分层、工具 schema、调用协议、错误语义、审批/幂等、安全、上下文、日志/Trace 和测试。
5. 对高风险结论执行无外部副作用的离线复现，包括：
   - 携带消息历史时动态系统提示词是否重新求值；
   - 生产工具注册后结构化失败是否仍能被 Harness 识别；
   - 系统提示词、工具描述和参数 schema 的本地字符规模。
6. 给出保留项、差距矩阵、目标分层和按依赖排序的分阶段路线图，不直接实现重构。

## 关键设计判断

- XML / Markdown 是模型可读的分段手段，不是 OpenAI、Anthropic 或 MCP 的工具调用协议，也不是安全边界。
- 权限、审批、参数校验、幂等、超时、重试和审计必须由运行时 Harness 机械执行，不能依赖提示词服从。
- 系统提示词只保存稳定身份、硬边界说明和任务策略；工具用途放在随实际暴露工具投影的描述/schema 中；玩家内容和工具结果作为不可信数据进入较低信任层。
- 建议基于评测决定是否采用 XML，而不是做全量格式迁移。跨 provider 应保持语义一致，允许渲染格式按模型族调整。
- 报告将优先修复已确认的语义和安全问题，再讨论提示词美化、动态工具检索或更复杂的多 Agent 架构。

## 质量门槛

- 术语符合 `CONTEXT.md`；玩家相关链路显式保留 `player_name` / `sender`。
- 所有本地关键证据使用相对路径和当前快照行号。
- 所有外部核心事实有可点击的一手来源；不引用搜索结果页。
- 不写入密钥、本地配置值、真实日志正文或闭源系统提示词猜测。
- Markdown 通过 `git diff --check`、链接格式、相对路径存在性、行号边界和来源数量检查。
