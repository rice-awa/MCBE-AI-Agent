# 方案六：让 AgentRuntime 真正负责组装与生命周期

## 目标

在应用启动位置明确组装并交付 `AgentRuntime` 拥有的模块，让初始化、关闭和状态替换具有清楚归属；逐步折叠没有额外行为的模块级全局转发函数。方向合理，但收益依赖方案四的职责划分，**不适合作为第一步**。

## 范围

- `services/agent/runtime.py:31-271`
- `services/agent/core.py:510-514`、`prompt.py:404-408`、`core/conversation.py:994-1001`、`mcp.py:482-486`、`providers.py:386-394`（模块级获取函数转发到全局 `_default_runtime`）

## 现状问题

`AgentRuntime` 实际拥有 MCBE Chat Agent 管理器、MCP 管理器、提示管理器、对话管理器、审批存储、模型元数据和工具审计写入器的生命周期，并提供统一初始化与关闭流程。但多个模块仍各自提供模块级获取函数再转发到全局 `_default_runtime`；`providers.py` 通过 `get_agent_runtime()` 直接读取/替换 `runtime_adapters`。名义所有权集中在 `AgentRuntime`，调用和测试却仍绕回多个全局入口。

这些获取函数本身几乎不隐藏行为，按删除检验删除它们不会让复杂度散回调用方，属于浅层转发。

## 验收标准

- [ ] 启动、关闭和重新启动不会复用过期的管理器。
- [ ] 一个运行时实例的替换不会污染其他测试。
- [ ] 审批存储、工具审计和模型提供方客户端只关闭一次。
- [ ] MCP 重载后工具集刷新仍由同一运行时负责。
- [ ] 测试不再需要同时替换多个模块级获取函数。

## 必须保留的约束

- 不演变为全仓一次性依赖注入改造。
- 不为只有一个实现的管理器创建假想适配位置。
- 应先完成/明确方案四的单次执行职责，再判断 `AgentWorker`、网关和测试真正需要从运行时获得什么。

## 删除检验（存在价值依据）

删除浅层获取函数不会丢失业务能力，说明这些转发函数没有足够深度；删除 `AgentRuntime` 本身会让初始化、关闭和多个管理器所有权重新分散，所以应加深 `AgentRuntime`，而非再套一层新模块。

## 验收门 / 回滚门（报告 12.1）

- **验收**：移除的浅层转发函数数 > 0；测试不再需要同时替换多个模块级获取函数。
- **回滚**：折叠后初始化/关闭复用了过期管理器，或跨测试污染。
