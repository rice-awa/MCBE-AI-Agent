# 方案一：收拢运行时 Harness 工具执行生命周期 — 技术设计

## 边界与契约

目标不是增加更多公开类或抽象接口，而是让已有两条路径共享同一套状态变化和收尾规则。内部深模块负责"提出、预检、决策、暂停与恢复、执行、结果归一、工具审计和追踪收尾"。

```
execute(start: ExecutionStart) -> UnifiedResult
# 普通执行与审批恢复各自构造不同的 ExecutionStart
# 内部统一收尾：预检 → 决策 → 暂停/恢复 → 执行 → 结果归一 → 工具审计 → 追踪
```

- `ExecutionStart`：携带两条路径各自的起始状态（普通执行：工具调用意图 + 参数；审批恢复：已冻结的 `plan_id` + 缓存计划）。
- `UnifiedResult`：统一的结果/决策/状态输出，供外层转换为 PydanticAI 工具返回值。

> 以上为职责边界草图，非最终签名或公开 API。实施前结合当前 `dev` 代码实际签名确定，避免套用报告中的旧行号。

## 数据流

1. 提出工具调用意图与参数。
2. 方块预检与参数投影（若有）。
3. 规则决策：允许 / 拒绝 / 需要审批。
4. 需要审批 → 冻结计划，挂起，返回可恢复的 `plan_id`。
5. 执行（普通执行直接执行；审批恢复从缓存读取已冻结计划后执行）。
6. 结果归一与异常分类。
7. 工具审计（失败不阻断主流程）。
8. 追踪收尾。

普通执行与恢复执行在步骤 1/4 的起始状态不同，但从步骤 5 起共享同一收尾链。

## 关键权衡

- **不新增公开抽象**：目标是把重复收尾收拢，而非创造新的适配层。若某个断言是"两条路径都必须满足"，则放入深模块；若某行为仅一条路径独有，保留在对应路径。
- **幂等**：幂等命中与写入在深模块内统一处理，普通执行与恢复执行共用同一套幂等键与写入逻辑。
- **工具审计失败容忍**：审计写入是旁路，异常捕获后继续主流程，这是既有约定，必须保持。

## 兼容性

- PydanticAI 工具调用接口、现有工具接口、Addon 适配方式、mcbews v1 协议均不变。
- 对外行为（三种决策、`plan_id` 恢复、幂等命中、异常分类）保持不变，仅内部实现收敛。

## 回滚形态

改动保持在 `execution.py` 内部，外部接口与测试文件名不强制变动。若验收门不满足（出现第二份收尾实现或路径行为不一致），可回退到拆分前版本，风险集中在单文件。

## 测试策略

通过现有接口建立特征测试（报告"建议验证的行为"六项），再移动实现。新增/调整测试覆盖普通执行与恢复执行的审计/追踪/幂等一致性。
