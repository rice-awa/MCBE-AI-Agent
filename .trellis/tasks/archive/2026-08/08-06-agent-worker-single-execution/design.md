# 方案四：把单次执行从 AgentWorker 生命周期中独立 — 技术设计

## 边界与契约

`AgentWorker` 保留：队列消费、按玩家取锁、任务启动/停止。

单次执行深模块负责：历史读取与清理、模型与依赖准备、流式输出、工具审批暂停与恢复、部分历史挽救、对话标题安排、追踪与分片关联、成功/取消/超时/异常收尾。

`AgentWorker` 只提交一次执行所需上下文，接收有限、可观察的结果。内部可由多个私有实现协作，**不是把大函数机械切成许多小函数**。

## 数据流

```
队列请求 → AgentWorker 取玩家锁 → 构造单次执行上下文 → execute(request) -> ExecutionResult
                                                              ├ 成功
                                                              ├ 审批挂起(plan_id)
                                                              ├ 部分可保存结果
                                                              ├ 超时 / 取消
                                                              └ 异常 / 连接断开
```

`AgentWorker` 收到 `ExecutionResult` 后决定：是否提交历史、是否安排标题生成、如何收尾追踪。历史提交/标题/追踪各**恰执行一次**。

## 关键权衡

- **不机械切碎**：目标是让测试通过稳定接口（单次执行结果）验证，而非了解多个内部入口和全局状态。若内部拆成多个私有实现，也应对 `AgentWorker` 暴露单一可观察入口。
- **测试表面**：当前测试替换大量全局入口（`stream_chat`、模型获取、管理器、MCP、运行时）。重构后测试应主要面向"单次执行结果"，减少替换个数。
- **不分层抽象**：不为只有一个实现的依赖创建接口。

## 兼容性

- 队列与玩家锁归属不变。
- `player_name` 从请求显式传入。
- 分片关联与下行发送路径不变。

## 回滚形态

单次执行深模块在 `worker.py` 内收敛（或同一模块新增私有组合）。若验收门不满足（测试反而更深耦合私有实现 / 单次执行仍混在队列生命周期里），回退。风险高（报告标 L），需稳打稳扎，先建特征测试再移动实现。

## 测试策略

面向"单次执行结果"建立特征测试，覆盖报告"建议验证的行为"七项（成功、审批挂起与恢复、部分结果、超时/取消、不可恢复异常、连接断开、收尾各执行一次）。逐步替换现有对 `_process_request_locked` 的直接调用。
