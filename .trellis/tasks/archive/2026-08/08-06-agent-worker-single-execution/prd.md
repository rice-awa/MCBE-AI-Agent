# 方案四：把单次 MCBE Chat Agent 执行从 AgentWorker 生命周期中独立

## 目标

保留 `AgentWorker` 对队列、玩家锁和任务生命周期的所有权，把一次请求的准备、执行与恢复、输出转换、失败挽救、历史提交和收尾集中到一个内部深模块。让 `AgentWorker` 只提交一次执行所需的上下文，并接收有限、可观察的执行结果。

## 范围

- `services/agent/worker.py:379-1207`（`_process_request_locked` 一段 829 行）
- `services/agent/worker.py:1295-1861`
- `services/agent/core.py`、`core/conversation.py`、`services/agent/context.py`

## 现状问题

`AgentWorker` 外部职责清楚（消费请求、按玩家取锁、管理任务启动/停止），但 `_process_request_locked` 一段 829 行同时承担历史读取/清理、模型与依赖准备、流式输出、工具审批暂停与恢复、部分历史挽救、对话标题安排、追踪与分片关联、成功/取消/超时/异常收尾。测试层已暴露接口过深依赖内部实现的信号：4 个测试文件共 23 次直接调用 `_process_request_locked`；存在大量对 `stream_chat`、模型获取、管理器、MCP 管理器、运行时全局入口的替换。

## 验收标准

- [ ] 普通成功执行收敛到单次执行模块。
- [ ] 审批挂起与恢复收敛到单次执行模块。
- [ ] 可保存的部分结果处理。
- [ ] 超时和取消处理。
- [ ] 不可恢复异常处理。
- [ ] 连接在执行中断开处理。
- [ ] 历史提交、标题生成和追踪收尾各执行一次。
- [ ] 测试直接调用 `_process_request_locked` 等私有方法的次数明显下降，替换模块级获取函数的数量减少。

## 必须保留的约束

- 队列和玩家锁仍由 `AgentWorker` 管理。
- `player_name` 必须从请求显式传入。
- 不改变现有分片关联和下行发送路径。
- 不把只有一个实现的内部依赖全部抽象成接口。

## 删除检验（存在价值依据）

若删除集中的单次执行模块，历史修复、分片关联、追踪收尾和保存规则会重新散回成功、取消、超时、审批和异常分支，因此它有明确存在价值。

## 验收门 / 回滚门（报告 12.1）

- **验收**：测试直接调用 `_process_request_locked` 等私有方法次数明显下降；替换模块级获取函数数量减少。
- **回滚**：测试反而更深耦合内部实现，或单次执行仍混在队列生命周期里。
