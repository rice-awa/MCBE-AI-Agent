# 方案二：让玩家身份始终来自当前事件（含安全门测试）

## 目标

先补同一连接（`connection_id`）下双玩家任务交错测试作为**安全门**，再消除连接级可变状态 `state._player_name` 对业务身份的兜底作用。玩家身份只能来自当前事件的 `event.sender` / 显式 `player_name`，并沿命令处理、会话读取、请求构造、回复、界面同步和审批归属显式传递。

## 范围

- `services/gateway/command_handlers.py:82-114,217-225,285-300,432-439,1013-1016`
- `services/gateway/hook.py:178-202`
- 连接级状态 `state._player_name` 的读写点。
- 相关测试（玩家身份、玩家桶隔离、双玩家交错）。

## 现状问题

约定要求同一世界通常只有一条 WebSocket 连接，多名玩家共享 `connection_id`，所有玩家状态必须用当前 `sender` / 显式 `player_name`。当前代码多数命令路径已显式传 `player_name`，但仍保留连接级可变状态 `state._player_name`：

- `handle_command` 和 `handle_ui_chat` 会更新它；
- 回复目标、`ChatRequest.sender`、界面同步和审批归属在缺少显式参数时回退到它；
- `HostConnectionHook` 用 `asyncio.create_task` 并发调度玩家消息和界面消息。

由此可推导竞态窗口：玩家 A 任务写入身份后等待，玩家 B 任务覆盖连接状态，玩家 A 若走到回退分支则读取到玩家 B 身份。这是**基于代码路径的风险推断**，非已证实事故。现有测试覆盖单玩家身份传递和玩家桶隔离，但缺少"同一连接、两名玩家、任务交错、恰好走回退分支"的完整测试。

## 验收标准

- [ ] 新增双玩家交错测试可控制调度顺序，覆盖请求、回复、界面同步和审批归属。
- [ ] 同一 `connection_id` 下玩家 A 与玩家 B 的命令交错执行时，两人 `ChatRequest.player_name` 不串扰。
- [ ] 回复目标与界面同步目标不串扰。
- [ ] 审批项只归属于发起工具调用的玩家。
- [ ] 对话、模板、变量、模型和上下文继续按玩家隔离。
- [ ] 缺少身份时明确失败或使用非业务性显示默认值，不落入其他玩家桶。
- [ ] 所有回退分支不再读取 `state._player_name` 作为业务身份来源。

## 必须保留的约束

- 当前事件的 `sender` / `player_name` 是唯一业务身份来源。
- 不使用 SDK 的连接级玩家属性（`ConnectionState.player_name`）做业务分支。
- 下行长文本继续经过 `BrokerResponseBridge` 或 SDK 下行模块。
- 不改变按 `(connection_id, player_name)` 分桶的既有约定。

## 删除检验（存在价值依据）

如果没有统一的按玩家处理规则，身份与会话、请求、回复、审批和追踪之间的关联会继续散落在每个命令处理函数里，因此这些规则应该集中维护。

## 验收门 / 回滚门（报告 12.1）

- **验收**：新增双玩家交错测试通过；所有回退分支不再读取 `state._player_name`。
- **回滚**：任一业务身份仍可能落到其他玩家桶，或测试无法可靠复现交错。
