# 方案三：集中 block_ops 宿主侧报文准备 — 技术设计

## 边界与契约

把以下规则集中到一个深模块，三个稳定工具 `inspect_block` / `place_block` / `fill_block` 只提交意图和参数，使用集中处理后的结果：

- 目标归一化（相对/绝对坐标、单点/区域）；
- 限制注入（数量限制）；
- 命令行字节预算；
- Addon 报文准备；
- 预检计划与冻结/审批恢复；
- 结果裁剪与统一错误格式。

`bridge.py` 继续承担 Addon 通信适配，不被工具实现重新接管。

## 数据流

```
工具意图 + 参数 → 目标归一化 → 限制/预算注入 → 预检计划 → [冻结 plan_id / 审批] → Addon 报文 → 执行 → 结果归一（成功/部分失败/未知/超限）
```

- `target.py` 只负责目标归一化，不再在函数内反向导入 `tools_impl` 来套限制；限制/预算逻辑上移到共享深模块。
- 三个工具对同类错误输出一致结果格式。

## 关键权衡

- **消除反向依赖**：`target.py` → `tools_impl` 的循环依赖必须解除。将限制注入/载荷准备上移到深模块，`target.py` 只做纯目标归一化。
- **收窄出口**：`block_ops/__init__.py` 只暴露桥、能力缓存、预检缓存和三个工具等稳定入口，不再重导出内部实现的零散名称。
- **不复制 Addon 规则**：报告 10.2 明确 Addon 的 `handleFill` / `handleInspectBlock` 已是有价值的深模块，宿主侧优化不应把那些规则复制回 Python。

## 兼容性

- 三个工具对外参数不变。
- mcbews v1 报文不变。
- 不恢复批量 `edit_blocks`。
- `bridge.py` 适配位置不变。

## 回滚形态

改动集中在 `block_ops/` 包内。若验收门不满足（仍存在反向依赖 / 错误结果不一致），回退到合入前提交。行为不变的预期使风险较低。

## 测试策略

复用方案一建立的方块工具生命周期特征测试；新增对目标归一化、数量限制、字节预算、预检/审批恢复、Addon 结果归一与三工具一致错误格式的测试。
