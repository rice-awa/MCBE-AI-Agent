# 方案五：让工具目录成为真实契约中心

## 目标

让工具目录负责内置工具的语义声明和注册时校验，并统一投影工具提示、风险策略、工具审计预览和参数说明。建立"一处声明、注册时核对、多个用途自动投影"的关系，减少工具语义、提示、注册和测试之间的手工同步。

## 范围

- `services/agent/harness/catalog.py:35-330`（`_TOOL_CATALOG`）
- `services/agent/harness/prompting.py:5-64`（方块工具优先级规则）
- `services/agent/prompt.py:29-38` 与 `services/agent/core.py:302-307`（重复的 `TOOL_USAGE_GUIDE`）
- `services/agent/tools.py:83-1256`（工具实现与文档字符串）
- `tests/test_runtime_harness_catalog.py`（手工维护 `REGISTERED_AGENT_TOOL_NAMES`）

## 现状问题

`_TOOL_CATALOG` 已集中记录工具意图、风险、适用场景、禁用场景、参数约束和审计预览，方向正确。但工具完整知识仍分散：实际名称/参数结构/长说明在 `tools.py`；方块工具优先级在 `harness/prompting.py`；`prompt.py` 与 `core.py` 各有一份 `TOOL_USAGE_GUIDE`；测试手工维护 `REGISTERED_AGENT_TOOL_NAMES`。目录虽被复用，但还没成为新增/修改工具时唯一需对齐的契约入口。

## 验收标准

- [ ] 每个已注册内置工具都有且只有一个目录条目。
- [ ] 目录中不存在未注册工具。
- [ ] 参数约束中引用的关键字段真实存在。
- [ ] 工具提示、风险策略和工具审计预览来自同一条目。
- [ ] MCP 工具有独立的来源标记和适配规则。
- [ ] 已移除工具不会残留在提示或目录中。

## 必须保留的约束

- 不在工具目录中复制完整参数结构（参数结构仍来自工具实现或 PydanticAI 注册结果）。
- 不把 MCP 工具强行改造成内置工具。
- 不让提示文字成为执行权限的唯一保障。
- 保留工具目录按"工具意图"组织的项目术语。

## 删除检验（存在价值依据）

若删除工具目录，工具意图、风险、适用场景和预览约束会重新散回提示、规则、工具审计和测试，因此它应继续加深，而非撤销。

## 验收门 / 回滚门（报告 12.1）

- **验收**：每个内置工具在目录中唯一；提示/风险/审计预览由同一条目投影。
- **回滚**：目录与实际注册结果出现不一致且无法自动核对。
