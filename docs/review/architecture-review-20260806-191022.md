## 一、结论摘要

项目当前没有需要推倒重来的结构性问题。现有架构已经形成了几处质量较高的深模块，例如下行消息发送、Addon 方块操作和配置装载。真正值得优化的地方，主要集中在近期频繁修改、规则重复、玩家身份依赖可变状态，以及测试不得不绕过公开接口触碰内部实现的区域。

本次审查得到六项候选方案：

1. **收拢运行时 Harness 的工具执行生命周期——强烈推荐，首要候选。** 统一普通执行与审批恢复的幂等、工具审计、追踪和收尾规则。
2. **让玩家身份始终来自当前事件——强烈推荐，安全优先。** 消除连接级 `state._player_name` 对业务身份的兜底作用，并先补充双玩家交错测试。
3. **集中 `block_ops` 的宿主侧报文准备——值得探索。** 消除目标处理与工具实现之间的反向依赖，集中载荷、限制、预算和预检规则。
4. **把单次 MCBE Chat Agent 执行从 `AgentWorker` 生命周期中独立出来——值得探索。** 让 `AgentWorker` 只负责队列、锁和任务生命周期。
5. **让工具目录成为真实的契约中心——值得探索。** 减少工具语义、提示、注册和测试之间的手工同步。
6. **让 `AgentRuntime` 真正负责组装与生命周期——试探性建议。** 方向合理，但收益依赖第四项的职责划分，不适合作为第一步。

综合建议是：**先为第二项建立并发安全测试，再推进第一项；第三至第五项按收益逐步处理，第六项最后重新评估。**

## 二、审查范围与方法

本次审查以项目约定中的术语和架构约束为准，重点阅读了：

- `CONTEXT.md`：运行时 Harness、工具目录、工具审计等共享术语；
- `CLAUDE.md`：多人会话隔离、SDK 下行、mcbews v1 协议和关键模块职责；
- `.trellis/workflow.md` 与 `.trellis/spec/`：项目工作流和分层规范；
- 最近 200 次提交的文件改动记录；
- 高频改动区域、超长实现、跨模块依赖和相关测试；
- 当前完整 Python 测试集。

评估时主要使用以下判断方式：

- **深模块**：调用方只需要了解较小的接口，复杂规则由模块内部吸收。
- **集中性**：同一类规则、故障和验证是否集中在一个地方，而不是散落到多个调用方。
- **复用收益**：一处实现是否能让多条调用路径和多组测试共同受益。
- **删除检验**：假设删除该模块；如果复杂度会重新散回多个调用方，说明模块有存在价值；如果复杂度反而消失，说明它可能只是浅层转发。
- **测试表面**：调用方和测试是否能够经过同一个稳定接口验证行为。

仓库中未发现 `docs/adr/` 或其他明确的架构决策记录目录，因此本报告主要依据代码、测试、项目说明和提交历史进行判断。

## 四、候选方案一：收拢运行时 Harness 的工具执行生命周期

推荐等级：**强烈推荐，首要候选**

主要位置：

- `services/agent/harness/execution.py:943-1425`
- `services/agent/harness/execution.py:1633-1796`
- `tests/test_runtime_harness_execution.py`
- `tests/test_block_ops.py`

### 发现的问题

`HarnessToolset.call_tool` 的对外入口并不复杂，但内部同时处理以下规则：

- 工具调用提出和追踪；
- 方块操作预检与参数投影；
- 规则判断和拒绝；
- 审批挂起；
- 幂等命中与写入；
- 实际工具执行；
- 异常分类和结果转换；
- 工具审计；
- 追踪收尾。

审批通过后的恢复路径 `_resume_approved_block_plan` 又重新处理了一部分相同生命周期，包括缓存读取、工具与计划匹配、幂等、执行、工具审计、追踪和结果转换。代码注释也明确说明该路径在“镜像主路径”。这意味着普通执行和审批恢复虽然起点不同，却各自维护相似的收尾规则。

风险不在于函数长，而在于**相同状态变化有两个实现位置**。以后调整工具审计字段、追踪状态、幂等规则或错误分类时，很容易只改到其中一条路径。

### 优化方向

保留 PydanticAI 现有接入位置、现有工具接口和 Addon 适配方式，把“提出、预检、决策、暂停与恢复、执行、结果归一、工具审计和追踪收尾”集中到一个内部深模块。普通执行和审批恢复只负责提供不同的起始状态，不再分别维护完整收尾流程。

这里不建议先增加更多公开类或抽象接口。首要目标是让已有两条路径共享一套状态变化和收尾规则。

### 删除检验

如果删除统一执行流程，审批、幂等、工具审计和追踪逻辑会重新散回每个工具、恢复分支和 `AgentWorker`，因此这个模块能够产生明确的集中性与复用收益。

### 建议验证的行为

- 允许、拒绝和需要审批三种决策；
- 审批挂起后通过 `plan_id` 恢复；
- 重复调用的幂等命中；
- 参数投影失败、工具异常和 Addon 异常；
- 工具审计失败时主流程继续运行；
- 普通执行与恢复执行产生一致的追踪和结果状态。

### 必须保留的约束

- 方块工具必须先预检，再进入审批判断；
- `plan_id` 只用于恢复已冻结计划，不携带隐藏执行参数；
- 工具审计失败不得阻断 MCBE Chat Agent；
- 不改变 PydanticAI 工具调用接口和现有 mcbews v1 适配方式。

## 五、候选方案二：让玩家身份始终来自当前事件

推荐等级：**强烈推荐，安全优先**

主要位置：

- `services/gateway/command_handlers.py:82-114`
- `services/gateway/command_handlers.py:217-225`
- `services/gateway/command_handlers.py:285-300`
- `services/gateway/command_handlers.py:432-439`
- `services/gateway/command_handlers.py:1013-1016`
- `services/gateway/hook.py:178-202`

### 发现的问题

项目约定明确要求：同一世界通常只有一条 WebSocket 连接，多名玩家共享 `connection_id`，所有玩家相关状态都必须使用当前事件的 `sender` 或显式 `player_name`。

当前代码已经在大多数命令路径中显式传递 `player_name`，但仍保留连接级可变状态 `state._player_name`：

- `handle_command` 和 `handle_ui_chat` 会更新它；
- 回复目标、`ChatRequest.sender`、界面同步和审批归属会在缺少显式参数时回退到它；
- `HostConnectionHook` 会用 `asyncio.create_task` 并发调度玩家消息和界面消息。

因此可以推导出一个竞态窗口：玩家 A 的任务写入身份后发生等待，玩家 B 的任务随后覆盖连接状态，玩家 A 如果走到某个回退分支，就可能读取到玩家 B 的身份。

这是一项**基于代码路径的风险推断**，不是已经证实的生产事故。现有测试覆盖了单玩家身份传递和玩家桶隔离，但没有发现“同一连接、两名玩家、任务交错、恰好走回退分支”的完整测试。

### 优化方向

玩家身份只能来自当前事件，并沿命令处理、会话读取、请求构造、回复、界面同步和审批归属显式传递。连接级状态可以保留与连接本身有关的信息，但不应再作为业务身份来源。

在调整实现前，应先增加一个可控制调度顺序的双玩家交错测试，用它证实风险窗口并作为后续重构的安全门。

### 删除检验

如果没有统一的按玩家处理规则，身份与会话、请求、回复、审批和追踪之间的关联会继续散落在每个命令处理函数里，因此这些规则应该集中维护。

### 建议验证的行为

- 同一 `connection_id` 下玩家 A 与玩家 B 的命令交错执行；
- 两人的 `ChatRequest.player_name` 不串扰；
- 回复目标和界面同步目标不串扰；
- 审批项只归属于发起工具调用的玩家；
- 对话、模板、变量、模型和上下文继续按玩家隔离；
- 缺少身份时明确失败或使用非业务性的显示默认值，不落入其他玩家桶。

### 必须保留的约束

- 当前事件的 `sender` / `player_name` 是唯一业务身份来源；
- 不使用 SDK 的连接级玩家属性进行业务分支；
- 下行长文本继续经过 `BrokerResponseBridge` 或 SDK 下行模块（`McbeOutboundDelivery` / `McbewsV1Delivery`）；
- 不改变按 `(connection_id, player_name)` 分桶的既有约定。

## 六、候选方案三：集中 `block_ops` 的宿主侧报文准备

推荐等级：**值得探索**

主要位置：

- `services/agent/block_ops/tools_impl.py`
- `services/agent/block_ops/target.py:275-298`
- `services/agent/block_ops/__init__.py:3-89`
- `services/agent/block_ops/bridge.py`
- `services/agent/block_ops/preflight_cache.py`

### 发现的问题

`tools_impl.py` 同时包含目标归一化后的处理、载荷构建、限制注入、命令行字节预算、预检、计划执行和结果处理。它在模块顶部依赖 `target.py`，而 `target.py` 为了给载荷应用限制，又在函数内部反向导入 `tools_impl.apply_limits_to_payload`。

函数内导入避免了导入阶段直接报错，但没有消除职责反向依赖，只是把循环关系藏了起来。与此同时，`block_ops/__init__.py` 重新导出了桥接、能力缓存、限制、预检缓存、结果构建和工具实现中的大量名称，使包的实际接口偏大，调用方更容易依赖内部细节。

### 优化方向

把宿主侧的目标归一化、限制规则、字节预算、Addon 报文、预检计划和结果裁剪集中到一个深模块。`inspect_block`、`place_block`、`fill_block` 三个稳定工具只提交意图和参数，并使用集中处理后的结果。

`bridge.py` 应继续承担 Addon 通信适配，不应把协议调用细节重新塞回工具实现。

### 删除检验

如果删除集中规则，查看、单格放置和区域填充会各自重新实现载荷、限制、预算和预检语义，因此这组规则具有很高的复用收益。

### 建议验证的行为

- 相对坐标、绝对坐标、单点和区域目标归一化；
- 数量限制和命令行字节预算；
- 预检、冻结计划和审批恢复；
- Addon 返回成功、部分失败、未知状态和超限；
- 三个工具对同类错误使用一致的结果格式。

### 必须保留的约束

- 不改变 `inspect_block`、`place_block`、`fill_block` 的对外参数；
- 不恢复已经移除的批量 `edit_blocks`；
- 不改变 mcbews v1 报文；
- `bridge.py` 继续作为 Addon 适配位置。

## 七、候选方案四：把单次 MCBE Chat Agent 执行从 `AgentWorker` 生命周期中独立出来

推荐等级：**值得探索**

主要位置：

- `services/agent/worker.py:379-1207`
- `services/agent/worker.py:1295-1861`
- `services/agent/core.py`
- `core/conversation.py`
- `services/agent/context.py`

### 发现的问题

`AgentWorker` 的外部职责很清楚：从队列消费请求、按玩家获取锁、管理任务启动和停止。但 `_process_request_locked` 一段就有 829 行，同时承担：

- 历史读取和清理；
- 模型与依赖准备；
- 流式输出；
- 工具审批暂停与恢复；
- 部分历史挽救；
- 对话标题安排；
- 追踪与分片关联；
- 成功、取消、超时和异常收尾。

测试层已经暴露出接口过深依赖内部实现的信号：4 个测试文件共 23 次直接调用 `_process_request_locked`；与 `AgentWorker` 测试相关的文件中，还存在大量对 `stream_chat`、模型获取、MCBE Chat Agent 管理器、MCP 管理器和运行时全局入口的替换。

这说明当前测试表面不是稳定的“单次执行结果”，而是一个需要了解多个内部入口和全局状态的搭建过程。

### 优化方向

保留 `AgentWorker` 对队列、玩家锁和任务生命周期的所有权，把一次请求的准备、执行与恢复、输出转换、失败挽救、历史提交和收尾集中到一个内部深模块。

这不是把大函数机械切成许多小函数。目标是让 `AgentWorker` 只提交一次执行所需的上下文，并接收有限、可观察的执行结果；内部可以继续由多个私有实现协作。

### 删除检验

如果删除集中的单次执行模块，历史修复、分片关联、追踪收尾和保存规则会重新散回成功、取消、超时、审批和异常分支，因此它有明确存在价值。

### 建议验证的行为

- 普通成功；
- 审批挂起与恢复；
- 可保存的部分结果；
- 超时和取消；
- 不可恢复异常；
- 连接在执行中断开；
- 历史提交、标题生成和追踪收尾各执行一次。

### 必须保留的约束

- 队列和玩家锁仍由 `AgentWorker` 管理；
- `player_name` 必须从请求显式传入；
- 不改变现有分片关联和下行发送路径；
- 不把只有一个实现的内部依赖全部抽象成接口。

## 八、候选方案五：让工具目录成为真实的契约中心

推荐等级：**值得探索**

主要位置：

- `services/agent/harness/catalog.py:35-330`
- `services/agent/harness/prompting.py:5-64`
- `services/agent/prompt.py:29-38`
- `services/agent/core.py:302-307`
- `services/agent/tools.py:83-1256`
- `tests/test_runtime_harness_catalog.py`

### 发现的问题

现有 `_TOOL_CATALOG` 已经集中记录了工具意图、风险、适用场景、禁用场景、参数约束和审计预览，这是正确方向。但工具的完整知识仍分散在多处：

- 实际名称、参数结构和长说明位于 `tools.py` 的工具函数与文档字符串；
- 方块工具优先级规则位于 `harness/prompting.py`；
- `prompt.py` 和 `core.py` 各自存在一份 `TOOL_USAGE_GUIDE`；
- 测试手工维护 `REGISTERED_AGENT_TOOL_NAMES`；
- 工具目录、实际注册结果和参数结构依靠多组测试分别检查。

因此工具目录虽然被提示、规则和工具审计复用，还没有成为新增或修改工具时唯一需要对齐的契约入口。名称、提示和参数发生变化时，维护者仍需知道多处隐含同步点。

### 优化方向

让工具目录负责内置工具的语义声明和注册时校验，并由它统一投影工具提示、风险策略、工具审计预览和参数说明。实际参数结构仍应来自工具实现或 PydanticAI 的注册结果，避免在目录里重新手写一份参数模型。

重点不是让一个文件保存所有文字，而是建立“一处声明、注册时核对、多个用途自动投影”的关系。

### 删除检验

如果删除工具目录，工具意图、风险、适用场景和预览约束会重新散回提示、规则、工具审计和测试，因此它应该继续加深，而不是撤销。

### 建议验证的行为

- 每个已注册内置工具都有且只有一个目录条目；
- 目录中不存在未注册工具；
- 参数约束中引用的关键字段真实存在；
- 工具提示、风险策略和工具审计预览来自同一条目；
- MCP 工具有独立的来源标记和适配规则；
- 已移除工具不会残留在提示或目录中。

### 必须保留的约束

- 不在工具目录中复制完整参数结构；
- 不把 MCP 工具强行改造成内置工具；
- 不让提示文字成为执行权限的唯一保障；
- 保留工具目录按“工具意图”组织的项目术语。

## 九、候选方案六：让 `AgentRuntime` 真正负责组装与生命周期

推荐等级：**试探性建议**

主要位置：

- `services/agent/runtime.py:31-271`
- `services/agent/core.py:510-514`
- `services/agent/prompt.py:404-408`
- `core/conversation.py:994-1001`
- `services/agent/mcp.py:482-486`
- `services/agent/providers.py:386-394`

### 发现的问题

`AgentRuntime` 已经实际拥有 MCBE Chat Agent 管理器、MCP 管理器、提示管理器、对话管理器、审批存储、模型元数据和工具审计写入器的生命周期，也提供统一初始化与关闭流程。

但多个模块仍各自提供模块级获取函数，再转发到全局 `_default_runtime`。此外，`providers.py` 会通过 `get_agent_runtime()` 直接读取或替换 `runtime_adapters`。结果是：名义上的所有权集中在 `AgentRuntime`，调用和测试却仍绕回多个全局入口。

这些获取函数本身几乎不隐藏行为。按删除检验来看，删除它们并不会让复杂度散回调用方，只会让调用方直接面对 `AgentRuntime`，所以它们更接近浅层转发。

### 优化方向

在应用启动位置明确组装并交付 `AgentRuntime` 拥有的模块，让初始化、关闭和状态替换具有清楚归属；逐步折叠没有额外行为的全局转发函数。

不过，这项调整不应演变为全仓一次性依赖注入改造，也不应为只有一个实现的管理器创建假想适配位置。应先完成或明确第四项的单次执行职责，再判断 `AgentWorker`、网关和测试真正需要从运行时获得什么。

### 删除检验

删除浅层获取函数不会丢失业务能力，说明这些转发函数没有产生足够深度；但删除 `AgentRuntime` 本身会让初始化、关闭和多个管理器的所有权重新分散，所以应该加深 `AgentRuntime`，而不是再套一层新模块。

### 建议验证的行为

- 启动、关闭和重新启动不会复用过期的管理器；
- 一个运行时实例的替换不会污染其他测试；
- 审批存储、工具审计和模型提供方客户端只关闭一次；
- MCP 重载后工具集刷新仍由同一运行时负责；
- 测试不再需要同时替换多个模块级获取函数。

## 十、有意保留的设计

### 10.1 `BrokerResponseBridge` 与 SDK 下行模块

这一组模块已经具有较好深度：调用接口较小，内部隐藏 tellraw、scriptevent、`mcbews:text_resp`、分片和流控细节。删除它们会使协议与分片复杂度散回所有下行调用方，因此不应因文件或逻辑较多而拆散。

### 10.2 Addon 的 `handleFill` 与 `handleInspectBlock`

这两个入口在 Addon 内部隐藏了预检、写入、回滚、查询和摘要规则。其复杂实现与较小入口相匹配，属于有价值的深模块。宿主侧优化不应把这些规则复制回 Python。

### 10.3 `services/agent/block_ops/bridge.py`

它负责宿主与 Addon 之间的适配，是已经存在且真实变化的接入位置。第三项优化应让上层报文准备更集中，但不应取消这一适配位置。

### 10.4 `config/settings.py`

文件虽然超过一千行，但配置读取、环境变量展开和验证规则已经集中，调用方复用收益高，而且近期不是主要改动热点。没有证据表明按行数拆分会改善接口或测试。

### 10.5 `core/conversation.py`

其中的依赖方向值得继续观察，但它与第四项和第六项的职责划分重叠。现在单独重构容易造成重复搬运，应先明确“单次执行”和“运行时所有权”分别负责什么，再决定对话管理最终位置。

## 十一、推荐推进顺序

### 第一步：建立安全门

先为候选方案二增加同一连接下双玩家任务交错测试。测试应覆盖请求、回复、界面同步和审批归属。即使暂时不重构，这项测试也能保护项目最重要的多人隔离约束。

### 第二步：实施首要架构优化

推进候选方案一，让普通工具执行与审批恢复共享状态变化和收尾规则。改动应保持内部化，不改变工具对外接口、PydanticAI 接入方式和 mcbews v1 协议。

### 第三步：整理方块操作宿主逻辑

在候选方案一稳定后处理候选方案三。两者都涉及方块预检和审批恢复，先统一工具生命周期可以减少后续 `block_ops` 调整时的重复工作。

### 第四步：改善单次执行的测试表面

推进候选方案四，把 `AgentWorker` 的队列生命周期与单次 MCBE Chat Agent 执行分开。此阶段重点观察测试是否能减少直接调用私有方法和替换全局入口。

### 第五步：统一工具契约知识

推进候选方案五，逐步消除重复的工具指南和手工名称集合，让目录、实际注册结果和提示投影形成可验证关系。

### 第六步：重新评估运行时所有权

候选方案四完成后再评估候选方案六。届时可以根据真实调用需求折叠浅层获取函数，避免现在凭假设进行全仓依赖改造。

## 十二、风险与实施原则

- 每次只处理一个候选方案，避免把架构优化变成跨仓库大搬迁。
- 优先通过现有接口建立特征测试，再移动实现。
- 不把大函数机械切碎；判断标准是接口是否更小、规则是否更集中、测试是否更接近调用方。
- 不为只有一个实现的依赖创建抽象接口；只有真实存在两种适配方式时，接入位置才有价值。
- 所有玩家相关路径继续显式传递 `player_name` / `sender`。
- 所有新增或修改的长文本下行继续经过 `BrokerResponseBridge` 或 SDK 下行模块。
- 保持 mcbews v1 线协议不变。
- 现有唯一测试失败需要单独跟踪，不应混入架构重构提交。

## 十三、最终建议

本项目当前最有价值的优化不是增加更多层次，而是把已经存在、但分散在多条路径中的规则收回到少数深模块。

首选目标是**运行时 Harness 工具执行生命周期**，因为它同时处在近期高频改动区域，并直接影响审批、幂等、工具审计、追踪和方块操作。与此同时，**玩家身份的双玩家交错测试应作为任何相关重构前的安全门**，因为多人会话隔离是项目明确写入架构约束的核心不变量。

建议下一轮先围绕候选方案一确定职责范围、不可改变的行为和迁移顺序，不急于设计具体类名或函数签名；候选方案二的并发测试可以作为同一轮的前置验证。
